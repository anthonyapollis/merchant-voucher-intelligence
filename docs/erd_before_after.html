Data model — before and after

What was delivered, what was built, and why each change was necessary
What is wrong with the delivered shape.
  • No date table — Every date is a string in four different files. Power BI time intelligence cannot work without a contiguous calendar.
  • Descriptive columns duplicated — Merchant, Region and Channel appear on three facts AND on the reference file — four places one value can disagree with itself.
  • No declared keys — MerchantID joins by string match. Nothing enforces that every value resolves, and nothing would notice if one stopped.
  • Everything is text — SalesValue, Transactions, ResolutionHours all arrive as strings. Any aggregate silently depends on implicit coercion.
  • No conformed dimensions — VoucherType, Priority, TicketType and Status exist only as repeated strings — no sort order, no grouping, no metadata.
  • Two grains, one shape — Daily aggregates and voucher-level rows look alike but count different populations: 510,127 transactions vs 120,969 vouchers.
Every arrow above is an enforced test. The dashed red arrows on the BEFORE diagram are implicit string joins that nothing validates. The teal arrows on the AFTER diagram are 15 relationships tests that run on every dbt build — drop a join and the build fails.
